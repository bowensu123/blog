vLLM · Continuous Batching Scheduler

忠实复现:每个 step 在三重物理约束下构建批次 — max_num_batched_tokens(计算量)、max_num_seqs(序列槽)、分页 KV cache 块(显存)。含 recompute 抢占与分块预填充同 step 产首 token。
原理 · 这个调度器在做什么

1 · 迭代级调度(为什么叫"持续"批处理)

早期的静态批处理(static batching)把一批请求绑成一个固定 batch,整批必须等其中最长的那条序列生成完才统一释放。由于不同请求的生成长度差异极大,先完成的序列只能空占算力与显存干等,GPU 利用率被长尾拖垮。设批内第 i 条序列实际生成 \(\ell_i\) 个 token、批大小为 \(M\),则静态批处理对算力的有效利用率为

\[ \eta \;=\; \frac{\sum_{i=1}^{M}\ell_i}{M \,\cdot\, \max_{i}\,\ell_i}\,. \]

长度方差越大,分母里的 \(\max_i \ell_i\) 被个别长序列拉高,\(\eta\) 越接近 \(0\)——这正是静态批处理的痛点。

vLLM 改用 iteration-level scheduling(迭代级调度):模型每跑完一次前向(一个 step / iteration),调度器就重新构建一次批次。关键观察是——自回归解码每个 step 对每条运行序列只产出 \(1\) 个 token,因此批次成员可以逐 step 自由进出而不付出额外代价:完成的序列立刻离场、归还它占用的 KV cache 块与序列槽,等待队列里的新请求立刻补位。成员持续流动,故称 continuous batching。

2 · 请求的两个相位与各自的瓶颈

  • Prefill(预填充):把整段 prompt 一次性并行喂入,一个 step 算出 prompt 全部 token 的 KV。长度 \(L\) 的 prompt 在该 step 贡献 \(L\) 个 token 的计算量,却只占 1 个序列槽。由于同一份模型权重被 \(L\) 个 token 复用,算术强度(arithmetic intensity)高 → 通常 compute-bound(算力受限)。
  • Decode(解码):自回归逐 token 生成,每个运行序列每 step 产 1 个 token、占 1 个序列槽。单 token 却要把整份权重与该序列的 KV cache 从显存读一遍,算术强度低 → memory-bandwidth-bound(显存带宽受限)。这也解释了为何 batch 对 decode 收益巨大:多条序列摊薄了同一次权重读取。

3 · 三重约束(调度的核心)

构建一个 step 的批次,本质是在三个相互独立的预算下做贪心装箱(greedy bin-packing)。设本 step 批内条目 \(i\) 消耗 \(t_i\) 个 token、其上下文长度为 \(\mathrm{ctx}_i\),块大小为 \(B\),则必须同时满足:

\[ \begin{aligned} \sum_i t_i &\;\le\; \ct{T_{\max}} && \text{单步计算量上限}\\[5pt] N \;(\text{批内序列条数}) &\;\le\; \cs{N_{\max}} && \text{batch 维度上限}\\[5pt] \sum_i \left\lceil \frac{\mathrm{ctx}_i}{B} \right\rceil &\;\le\; \ck{K} && \text{分页 KV 显存上限} \end{aligned} \]

三个上限分别对应控制面板的参数:\(\ct{T_{\max}}=\)max_num_batched_tokens、\(\cs{N_{\max}}=\)max_num_seqs、\(\ck{K}=\)num_gpu_blocks、\(B=\)block_size。每个条目在三个预算里的"成本"取决于它处于哪个相位:

相位token 成本 \(t_i\)序列槽KV 块占用主要受限于
prefillprompt 长度 \(L\)\(1\)\(\lceil L/B\rceil\)(随 \(L\) 增长)tokens / KV
decode\(1\)\(1\)每 \(B\) 个 token \(+1\) 块seqs / KV

三个预算里任意一个先归零就成为本 step 的瓶颈,且瓶颈会随相位切换:大量 prompt 涌入做 prefill 时 token 预算先耗尽 → token-bound;进入稳态 decode 后序列槽占满 → seq-bound;上下文累积、显存吃紧时 KV 块先用光 → KV-bound。

4 · 分页 KV cache 与抢占(PagedAttention)

KV cache 被切成固定大小的块(block),每块存 \(B\)(block_size)个 token 的 KV。承载 \(n\) 个 token 的上下文需要

\[ \left\lceil \frac{n}{B} \right\rceil \text{ 个块},\qquad \text{末块平均浪费 } \frac{B-1}{2} \text{ 个槽位(内部碎片)。} \]

块总数 \(\ck{K}\)(num_gpu_blocks)由显存容量决定,是一条硬上限。Decode 时,当且仅当上下文长度恰好跨过块边界才需要新分配 \(1\) 块:

\[ \left\lceil \tfrac{n+1}{B} \right\rceil > \left\lceil \tfrac{n}{B} \right\rceil \quad\iff\quad n \equiv 0 \pmod{B}. \]

当某个运行序列要追加 token 却无空闲块时,调度器触发抢占(preemption):按 FCFS 优先级,从运行集里挑优先级最低(最晚到达)的序列开刀。默认的 recompute 模式会——释放被抢占者的全部 KV 块、把它退回等待队列队头;待重新调度时,必须对 \(\text{prompt} + \text{已生成 token}\) 整段重新 prefill。也就是说,一个 prompt 长 \(L\)、已生成 \(g\) 个 token 的序列被抢占后,其 re-prefill 目标长度变为

\[ L_{\text{re}} \;=\; L + g \;\ge\; L, \]

这部分计算被白白重做,正是抢占的代价(因此本模拟器对被抢占序列的 re-prefill 目标会变长)。

关键:chunked prefill 不降低 KV 占用。它只把 prefill 的计算分摊到多个 step,削平算力尖峰;但整段 prompt 的 KV 最终都要常驻显存。因此只要一个请求满足

\[ \left\lceil \frac{L}{B} \right\rceil \;>\; \ck{K}, \]

它永远装不下 → vLLM 在准入时直接拒绝(本模拟器标为 aborted),且不会阻塞排在它后面的请求。

5 · Chunked prefill 与队头阻塞(HOL blocking)

关闭 chunked prefill 时,prefill 必须整段一次完成。若队头请求满足 \(L > \ct{T_{\max}}\),它单步塞不下又不可分割,在 FIFO 下会堵死整条队列(head-of-line block),后面再小的请求也只能干等。

开启 chunked prefill 后,长 prompt 被切成不超过 token 预算的多个 chunk。在不与 decode 混批的极端情形下,单独 prefill 它大致需要

\[ \left\lceil \frac{L}{\ct{T_{\max}}} \right\rceil \text{ 个 step}, \]

这些 chunk 跨 step 灌入,并可与其它序列的 decode 混批填满预算;且在最后一个 chunk 完成 prefill 的同一个 step 就采样出首 token(本模拟器复现了这一点)。这样既消除了 HOL 阻塞,又把 prefill 的算力尖峰摊平到多个 step 上。

调度循环 · 每个 step 的伪代码(含抢占)

下面就是本模拟器每个 step 实际执行的逻辑,对应 vLLM 统一(chunked-prefill)调度路径。三处与真实行为一致:running 优先、KV 块不足时按 FCFS 从尾部抢占(recompute)、prefill 完成同 step 采样首 token。

def schedule_step(running, waiting):
    bt = max_num_batched_tokens;  bs = max_num_seqs;  batch = []
    free = num_gpu_blocks - Σ ⌈ctx(r)/B⌉  for r in resident

    # ── 1. running-status(decode 与在飞的 chunked-prefill),优先级 = FCFS ──
    dq = sort(running ∪ prefilling, by=arrival)        # 队头=最高优先级
    while dq:
        seq = dq[0];  t = 1 if decode else min(remaining, bt)
        if bs < 1 or bt < 1:  break            # seq/token-bound
        need = ⌈(ctx+t)/B⌉ - ⌈ctx/B⌉                  # 跨块才需新块
        while need > free:                         # ── 抢占 ──
            if len(dq) > 1:  preempt_recompute(dq.pop())  # 牺牲最低优先级
            else:            preempt_recompute(seq); break     # 连自己也保不住
            free = recompute_free()
        schedule(seq, t);  bt -= t;  bs -= 1;  dq.popleft()
        if prefill_just_completed(seq):
            sample_first_token(seq)               # 同 step 产首 token

    # ── 2. waiting(新 prefill),FIFO ──
    for seq in sort(waiting, by=arrival):
        if bs < 1:  break
        target = seq.prompt + seq.generated           # 被抢占者含已生成 token
        if ⌈target/B⌉ > num_gpu_blocks:  abort(seq); continue  # 永远装不下
        chunk = min(target - seq.prefilled, bt) if chunked else full
        if chunk > bt:  break                     # token-bound / HOL
        if blocks(chunk) > free:  break            # KV-bound(等释放)
        admit(seq, chunk);  bt -= chunk;  bs -= 1
        if prefill_just_completed(seq):  sample_first_token(seq)
    return batch

四个可调参数 · what each knob means
max_num_batched_tokens — 单步 token 预算(计算量上限)。本 step 批内所有条目消耗的 token 之和不得超过它;prefill 一次吃 \(L\) 个 token,所以它主要压制 prefill 的算力尖峰。
max_num_seqs — 序列槽数(batch 宽度上限)。一个 step 最多并行多少条序列(prefill 或 decode 各占 1 槽)。这是 decode 稳态最常见的瓶颈。
num_gpu_blocks — 分页 KV cache 的物理块总数(显存硬上限)。所有常驻序列占用的块数 \(\sum_i \lceil \mathrm{ctx}_i/B\rceil\) 不得超过它;耗尽时触发 recompute 抢占。
block_size B — 每个 KV 块容纳的 token 数。越小内部碎片越少,但 decode 跨块边界更频繁、所需块数更多。
实验卡片里的 “设置 512 / 6 / 64 / B16” 按顺序表示 max_num_batched_tokens / max_num_seqs / num_gpu_blocks / block_size = 512 / 6 / 64 / 16。改某一项时,其余保持此默认值。

⑥ 块大小的影响

把 B 从 16 改成 8。块更细 → 内部碎片更少但块数需求更多;decode 更频繁跨边界,抢占更易触发。

设置:block_size = 8

配平直觉: tokens 控单步算力/prefill 尖峰;seqs 控批宽;KV 块 控可同时驻留的总上下文。三者任一先归零即成瓶颈,按你的 prompt:生成 长度比与显存来权衡。

已建模:迭代级调度、三重约束装箱、分页 KV、recompute 抢占(FCFS 选victim、回插队头、re-prefill 含已生成 token)、准入拒绝、chunked prefill 同 step 首 token。未建模(真实系统的其它可选机制):SWAP 抢占模式、prefix/前缀缓存复用、beam search、推测解码、跨请求 block 共享、watermark 在小规模下近似为 0。
