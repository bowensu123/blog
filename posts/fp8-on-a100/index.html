把 FP8 模型塞进 A100：
从浮点格式到反量化 kernel

模型是用 FP8 训练/发布的，但手头的卡是 A100。能跑吗？能 —— 但「能跑」这三个字背后，藏着硬件代际的硬约束。这篇从浮点格式的数学定义讲起，一路推到 A100 上三种落地方案的代码实现，并解释为什么缩放（scaling）才是整件事的命门。

FP8 · E4M3 / E5M2A100 / Ampere sm_80量化 · dequant

§ 0先把矛盾摆出来

一句话：A100（Ampere，sm_80）的 Tensor Core 没有 FP8 通路。原生 FP8 矩阵乘是从 Ada（sm_89）和 Hopper（sm_90）才进的硬件。所以在 A100 上，FP8 永远只能作为一种存储 / 搬运格式，真正的乘加要么回到 BF16/FP16，要么用 CUDA Core 模拟。

要理解这个约束的代价和绕法，得先把 FP8 到底是什么搞清楚。

§ 2FP8 ↔ BF16 的相互转换

A100 上的主力路线是把 FP8 转回 BF16 来算，所以转换是绕不开的一环。先列 BF16：1 符号 + 8 指数 + 7 尾数，bias = 127，动态范围与 FP32 同（指数位宽一致）。

2.1 FP8 → BF16：无损

关键观察：

即 BF16 的指数能装下任何 FP8 的量级，尾数位也更多。因此任意有限 FP8 值都能被 BF16 精确表示，转换是单射且无损的。流程只有三步：

  1. 指数重偏置：
  2. 尾数左对齐补零（2/3 位搬到 BF16 高位，低位填 0）
  3. 特殊值映射（E5M2 的 Inf/NaN、E4M3 的 NaN 各自转过去）

唯一的小陷阱：FP8 的次正规数转过去通常落在 BF16 的正规区（例如 E4M3 的 在 BF16 里远在正规范围内），需要做一次归一化 —— 把前导 1 移出、相应调整指数。结果仍然精确。

2.2 BF16 → FP8：有损，要舍入 + 饱和

这是真正需要小心的方向，四类边界：

  • 指数重偏置：（E5M2 减 112，E4M3 减 120）
  • 尾数舍入：7 位截到 2/3 位，标准做法 round-to-nearest-even（用 guard / round / sticky 三位判定），进位可能让指数 +1，要在判溢出之前处理。
  • 上溢：E5M2 可输出 Inf；E4M3 没有 Inf，按模式选择饱和到 448 或输出 NaN（训练里几乎总是饱和）。
  • 下溢： 进入次正规区，把有效位（含隐含 1）右移 位再舍入，再小则归零。

下面是 BF16 → E4M3 的参考实现（RNE 舍入 + 饱和）。改成 E5M2 只需把指数/尾数位宽与 bias 换掉，并把饱和分支换成输出 Inf：

C
#include <stdint.h>

// 入参为 BF16 的 16 位 raw，返回 E4M3 的 8 位 raw
uint8_t bf16_to_e4m3(uint16_t x) {
    const int BIAS_SRC = 127, BIAS_DST = 7;
    uint32_t s = (x >> 15) & 1;
    int32_t  e = (x >> 7) & 0xFF;
    uint32_t m =  x       & 0x7F;          // 7-bit 尾数

    if (e == 0xFF) return (s << 7) | 0x7F; // Inf/NaN -> E4M3 NaN（无 Inf）
    if (e == 0 && m == 0) return s << 7;   // ±0

    // BF16 次正规 -> 归一化成 (1.f, 调整 e)
    if (e == 0) { while (!(m & 0x80)) { m <<= 1; e--; } m &= 0x7F; e++; }

    uint32_t mant = 0x80 | m;              // 隐含 1 + 7 位 = 1.mmmmmmm
    int32_t  E = e - BIAS_SRC + BIAS_DST;  // 目标指数域

    int shift;                             // 需丢弃的低位数
    if (E <= 0) { shift = (7 - 3) + (1 - E); E = 0; } // 次正规：多移 (1-E)
    else        { shift = 7 - 3; }                    // 正规：7->3，丢 4 位
    if (shift > 8) return s << 7;          // 太小 -> 0

    // round-to-nearest-even（guard/round/sticky）
    uint32_t round  = 1u << (shift - 1);
    uint32_t sticky = (mant & (round - 1)) != 0;
    uint32_t q = mant >> shift;
    uint32_t r = mant & ((1u << shift) - 1);
    if (r > round || (r == round && (sticky || (q & 1)))) q++;

    if (q & 0x08) { q >>= 1; E++; }        // 舍入进位使尾数溢出 -> 指数 +1

    if (E >= 15 && !(E == 15 && (q & 7) <= 6))   // 超出 448 -> 饱和
        return (s << 7) | 0x7E;                  // 448 = S.1111.110

    return (s << 7) | ((E & 0xF) << 3) | (q & 0x7);
}
注　生产环境别手写位操作 —— PyTorch 原生有 torch.float8_e4m3fn / torch.float8_e5m2，x.to(...) 一行搞定，且与硬件路径一致。手写版只用于理解或无原生支持的环境。

§ 3为什么 A100 给不了原生 FP8 算力

3.1 架构代际

架构代表卡SM 版本Tensor Core 支持的输入类型
AmpereA100sm_80FP64, TF32, BF16, FP16, INT8, INT4
AdaL40, 4090sm_89以上 + FP8 (E4M3/E5M2)
HopperH100sm_90以上 + FP8，且引入 wgmma

A100 的 Tensor Core 指令集里，mma.sync 支持 .bf16 / .f16 / .tf32，但没有 .e4m3 / .e5m2 这条 MMA 通路。这条 FP8×FP8 → FP16/FP32 累加的硬件指令，要到 sm_89 / sm_90 才有。

3.2 这意味着什么

在 A100 上不存在「FP8 进、FP8 算」的硬件路径。任何 FP8 数据要参与计算，必须先被反量化（dequantize）回一个 Tensor Core 认识的类型（BF16/FP16），区别只在于「什么时候、在哪一级存储上做这次反量化」。这正好对应下面三条路线。

§ 4三条在 A100 上跑 FP8 的路线

4.1 路线一：全量反量化成 BF16（最常见、最稳）

把整个 FP8 权重张量 dequant 成 BF16，之后一切照常走 BF16 Tensor Core。DeepSeek-V3 这类 FP8 发布的模型，官方就提供这种转换脚本。

代价直白：显存翻倍（回到 BF16 的占用），完全拿不到 FP8 的速度，只是「能正确算出来」。

这里值得展开的是反量化不是裸 cast。DeepSeek 风格用的是 128×128 分块缩放（block-wise scaling）：权重以 E4M3 存，另存一份 FP32 的逐块缩放因子 scale。反量化公式，对块 内的元素：

Python
import torch

def weight_dequant_blockwise(
    w_fp8: torch.Tensor,   # [N, K], dtype=torch.float8_e4m3fn
    scale: torch.Tensor,   # [ceil(N/B), ceil(K/B)], dtype=torch.float32
    B: int = 128,
) -> torch.Tensor:
    N, K = w_fp8.shape
    w = w_fp8.to(torch.float32)                       # FP8 -> FP32（无损）
    # 把逐块 scale 展开回逐元素 [N, K]
    s = scale.repeat_interleave(B, dim=0).repeat_interleave(B, dim=1)
    s = s[:N, :K]                                     # 处理非整除的边界块
    return (w * s).to(torch.bfloat16)                 # 落回 BF16

# A100 上加载 FP8 权重后，转一次即可用普通 BF16 GEMM
W_bf16 = weight_dequant_blockwise(W_fp8, W_scale)     # 之后 x @ W_bf16.T 走 BF16 TC
为什么分块而非 per-tensor？　单一缩放因子要兼顾全张量的 absmax，会让小数值被压到 FP8 的次正规区甚至归零；128×128 分块让每块用各自的量级，显著降低量化误差。这点在 §5 细说。

4.2 路线二：Weight-only FP8 + 在线反量化 kernel（省显存）

思路：权重始终以 FP8 留在显存里，只在 GEMM kernel 把它从全局内存搬进寄存器的那一刻，即时 unpack 成 FP16 再喂给 Tensor Core。激活仍是 FP16/BF16。这样显存和访存带宽按 FP8 省，但计算精度和峰值算力还是 FP16 的。Marlin / Machete 这类 kernel 就是干这个的。

一个说明性的 Triton GEMV-with-dequant 内核骨架（per-block scale，沿 K 维分块）：

Python · Triton
import triton
import triton.language as tl

@triton.jit
def gemv_w8a16_kernel(
    x_ptr,            # 激活 [K],  fp16
    w_ptr,            # 权重 [N,K], 以 int8 存的 e4m3 raw bits
    s_ptr,            # 逐块 scale [N, K//BK], fp32
    y_ptr,            # 输出 [N],  fp16
    N, K, BK: tl.constexpr, BN: tl.constexpr,
):
    pid = tl.program_id(0)                       # 每个 program 负责 BN 行
    row = pid * BN + tl.arange(0, BN)            # [BN]
    acc = tl.zeros((BN,), dtype=tl.float32)

    for k0 in range(0, K, BK):                   # 沿 K 维分块
        k = k0 + tl.arange(0, BK)                # [BK]
        xv = tl.load(x_ptr + k).to(tl.float32)   # [BK]

        w_raw = tl.load(w_ptr + row[:, None] * K + k[None, :])  # [BN,BK] int8
        # —— 在寄存器里把 e4m3 raw bits 反量化成 fp32 ——
        w = e4m3_bits_to_fp32(w_raw)             # 位运算 unpack（§2.2 的逆）
        s = tl.load(s_ptr + row * (K // BK) + (k0 // BK))       # [BN] 该块 scale
        w = w * s[:, None]                       # 应用 per-block scale

        acc += tl.sum(w * xv[None, :], axis=1)   # 累加（等效用 FP16 TC 的位置）

    tl.store(y_ptr + row, acc.to(tl.float16))

（真实的 Marlin/Machete 远比这复杂：权重要做 bit-interleave 重排以匹配 Tensor Core 的 ldmatrix 布局、用 mma 而非标量乘加、做 software pipelining 掩盖延迟。上面只为展示「FP8 存储 + 寄存器内 dequant + FP16 计算」这条数据流。）

重要提醒　vLLM / SGLang 在 Ampere 上对 FP8 的支持大体走的就是这条 dequant 路子，而非真 FP8 算力。但这块软件栈更新很快 —— 具体哪些算子、哪些版本、哪种量化粒度支持 Ampere，务必以你要用的框架当前文档为准，别拿本文当事实标准。

4.3 路线三：软件模拟 FP8（基本只用于数值验证）

在 CUDA Core 上用整数/位运算把 FP8 算术整个模拟一遍（包括 §2 那套舍入逻辑）。慢得多，只适合验证量化算法的数值正确性、复现训练时的 FP8 行为做研究，不用于生产推理。它的唯一价值是「在没有 FP8 硬件的卡上，精确复刻有 FP8 硬件时的数值结果」。

§ 5缩放（scaling）才是真正的命门

前面反复出现 scale，这里说清楚为什么纯格式转换只是配角。

E4M3 的可表示窗口只有约 。一个典型的 BF16 权重/激活张量，数值集中在 量级，如果直接 cast，大量元素会掉进次正规区被严重量化、甚至下溢成 0 —— 得到一堆废数据。所以正确流程永远是：先用缩放因子把数值搬进 FP8 的甜区，再 cast；用的时候再除回去。

5.2 完整的量化—反量化对

Python
import torch

def quantize_to_fp8_blockwise(X: torch.Tensor, B: int = 128):
    """BF16/FP32 张量 -> (E4M3 权重, FP32 逐块 scale)。"""
    N, K = X.shape
    Xf = X.to(torch.float32)
    x_max = 448.0  # E4M3 上限

    # 逐 128x128 块求 absmax
    Np, Kp = (N + B - 1) // B, (K + B - 1) // B
    Xpad = torch.zeros(Np * B, Kp * B, dtype=torch.float32, device=X.device)
    Xpad[:N, :K] = Xf
    blocks = Xpad.reshape(Np, B, Kp, B)
    absmax = blocks.abs().amax(dim=(1, 3)).clamp(min=1e-12)   # [Np, Kp]
    scale = absmax / x_max                                    # [Np, Kp]

    # 用块 scale 归一化后 cast
    s_full = scale.repeat_interleave(B, 0).repeat_interleave(B, 1)
    Xq = (Xpad / s_full).to(torch.float8_e4m3fn)[:N, :K]
    return Xq, scale

def dequantize_from_fp8_blockwise(Xq, scale, B: int = 128):
    """逆操作，回到 BF16（对应 §4.1）。"""
    N, K = Xq.shape
    s = scale.repeat_interleave(B, 0).repeat_interleave(B, 1)[:N, :K]
    return (Xq.to(torch.float32) * s).to(torch.bfloat16)

# 往返误差检查
W = torch.randn(256, 512, dtype=torch.bfloat16) * 0.02       # 典型权重量级
Wq, s = quantize_to_fp8_blockwise(W)
W_hat = dequantize_from_fp8_blockwise(Wq, s)
rel = (W_hat.float() - W.float()).abs().mean() / W.float().abs().mean()
print(f"平均相对误差 ≈ {rel:.4f}")   # 量级与 2^-(3+1)=6.25% 的理论上界相符

跑出来的相对误差会落在 E4M3 理论上界 附近 —— 而如果把缩放去掉直接 cast，误差会因为大量下溢而失控。这就是缩放策略比格式转换本身重要的实证。

§ 6一页纸总结

你想要的A100 能给吗怎么做
正确跑出 FP8 模型的结果✅路线一：全量 dequant 到 BF16
省显存 / 省访存带宽（尤其解码）✅路线二：weight-only FP8 + 在线 dequant kernel
复刻 FP8 硬件的数值行为做验证✅（慢）路线三：软件模拟
FP8 原生算力加速（吞吐翻倍）❌需要 H100 / Ada，性能锁在 Hopper TC 里
  1. FP8 在 A100 上只是存储格式，不是计算格式。任何 FP8 数据参与运算前都要 dequant 回 BF16/FP16，差别只在反量化发生在哪一级存储。
  2. 格式转换是配角，缩放是主角。E4M3 窗口太窄，没有合适粒度的 scale，直接 cast 必然溢出/下溢成废数据。
  3. 想靠 FP8 把 A100 吞吐拉上去是拿不到的 —— 但靠 weight-only FP8 省显存、在访存受限的解码阶段提速，是实打实可行的。
